# AI 協作流程

> 貼進專案的 `AGENTS.md`（或 `CLAUDE.md`）。開 issue 後由 AI 改程式開 PR、在 GitHub 雲端審查（與選用的測試），都通過才通知使用者。
> 流程由 `.github/workflows/ai-dev.yml`、`ai-review.yml` 呼叫 `ai-dev-flow` 的共用流程；`<base 分支>`、變更記錄的寫法等依專案改寫，用不到的段落（例如測試）刪掉。
> 這一段是給參與流程的 agent（開發、審查、測試）看的；平常在本機跟使用者對話的 agent 照其他規則做即可。

## 角色

- **開發**（GitHub 雲端）：依照 issue 改程式、開 PR；依照審查與測試的留言修改自己開的 PR
- **審查**（GitHub 雲端）：只讀程式碼、在 PR 留言、給出結論，不改程式，也不執行測試
- **測試**（GitHub 雲端，選用）：審查通過才執行；在獨立測試環境實際操作驗證，不改程式
- **使用者**：可以開工的 issue 都是先跟 agent 討論過才建立；合併 PR、部署都由使用者決定

## 流程

1. 規劃好（寫好驗收條件）的 issue 才加 `bug` 或 `feature`，代表「可以開工」；沒有類型標籤的 issue 是「待規劃」。加上 `ai:subscription`（或專案設定的其他 `ai:<服務>`，代表用哪家 AI）時叫醒開發 agent；沒有指定用哪家的 PR 不審查、不測試
   - 開工檢查：issue 要有 `bug`／`feature` 標籤，而且內文有「## 驗收條件」段落、底下有內容。缺任何一樣就不叫醒開發 agent（不花額度），拿掉 `ai:*` 標籤、只發 Telegram 通知；補齊後重新加 `ai:*` 標籤即可。在 issue 留言 `@claude` 也一樣兩樣都要有
2. 開發 agent 改程式、開 PR 到 `<base 分支>`
3. PR 開啟或有新 commit 時先跑審查；同一個 PR 只保留最新一次，舊的自動取消
4. 審查通過才跑測試（專案有設定測試時）；都通過就通知使用者
5. 審查「需修改」或測試「失敗」時，由 workflow 叫醒開發 agent（告知 PR 編號與第幾輪），修完推上新 commit，回到第 3 步
6. 有寫入權限的人也可以在 issue 或 PR 留言 `@claude` 直接叫醒開發 agent

## 合併

- 只合併「最新 commit」審查（與測試）都通過的 PR：PR 上最新的審查總評與測試報告寫的版本，要等於 PR 目前的 head commit
- 審查「需修改」「可疑」、測試沒通過或沒有結論時，「AI 審查與測試」的 run 會顯示失敗；但合併前仍要讀留言確認結論與版本，不能只看 run 是綠的（被取消、固定檢查擋下、只改文件沒跑的 run 都不代表通過）
- 合併前推過任何 commit（包括把 base 分支合併進來解衝突），都要等那個版本重新審查、測試通過才合併
- 合併前確認 PR 分支上沒有進行中或排隊中的 workflow（`gh run list --branch <分支> --status in_progress` 與 `--status queued` 都要是空的）
- 合併一律用 `gh pr merge <編號> --match-head-commit <通過的 commit>`：分支在這之後又多了 commit，GitHub 會拒絕合併
- 被固定檢查擋下、不跑自動審查的 PR（改到規則、自動化設定或套件清單），以及只改文件沒跑審查的 PR，人工審查後合併，同樣鎖定審查過的那個 commit

## issue

- **可以開工**（有 `bug` 或 `feature` 標籤）：內容要包含背景、要做什麼、不要做什麼、驗收條件；需要使用者自己確認的另外寫在「## 使用者驗證」（選填）
- **待規劃**（沒有類型標籤）：只寫一兩句描述，不寫驗收條件；之後討論清楚、寫好驗收條件再加 `bug`／`feature`
- 驗收條件的格式：單獨一行、一字不差的 `## 驗收條件` 標題（不能寫成「驗收」「驗收標準」或粗體字），底下至少一條實際內容（範本的註解、空的 `1.` 不算）
- 驗收條件只寫審查與測試做得到的，要能逐條確認；只能讀程式碼確認的標「（讀程式碼確認即可）」；需要使用者自己確認的寫在「## 使用者驗證」，審查與測試不看這段
- 需求要寫到開發 agent 不用自己猜：要用的套件、工具或做法寫出確定的一個；有取捨的地方先跟使用者決定再寫進 issue
- 標籤：`bug`／`feature` = 可以開工（加上本身不會開工）；`ai:subscription`（或其他 `ai:<服務>`）= 開工；可再加 `model:claude-opus-5-5`／`model:claude-sonnet-5-5` 指定模型；`blocked` 由開發 agent 在做不出來時自己加；`round-N` 由 workflow 管理
- issue 不要要求 PR 修改受保護檔案（`AGENTS.md`、`CLAUDE.md`、`.claude/`、`.github/`、Dockerfile、compose 檔，以及專案另外指定的套件清單等）；需要改的話，開工前由使用者或本機 agent 直接改 `<base 分支>`

## 開發規則

- 從 `<base 分支>` 開分支，命名 `ai/issue-<編號>-<英文簡述>`；PR 一律開到 `<base 分支>`，說明裡寫 `Closes #<編號>`
- PR 說明要寫：改了什麼、影響、自己怎麼驗證的、沒驗證到什麼，以及「後續待辦」段落（這次沒做、之後要做或要注意的事，沒有就寫「無」）
- 變更記錄：`<這個專案的變更記錄寫法，例如在 changelog.d/ 新增一個小檔>`
- 不要修改規則與自動化設定（`AGENTS.md`、`CLAUDE.md`、`.claude/`、`.github/`），除非 issue 明確要求；改到這些的 PR 會被固定檢查擋下等使用者人工審查
- 做不出來時不要硬做出一個 PR：在 issue 留言說明卡在哪裡、需要使用者提供或決定什麼，加上 `blocked` 標籤後停止
- 被叫醒修改時：讀完 PR 上所有審查與測試的留言，一次修完再推上去，並逐條回覆每一個要求：已修改（附上改了哪裡），或不修改的理由

## 審查規則

- 只看這次觸發的版本：用 `git diff <base>...<head>` 看改動，不要用 `gh pr diff`
- 複審只看這輪改了什麼：先逐條確認上次的【高】／【中】修好了沒，再只審上次審查之後的改動；這輪沒改到、上次已經審過的程式，現在才發現的問題只能寫成【低】或「後續建議」，不擋 PR
- 結論三選一：**通過**（沒有【中】以上的問題）／**需修改**（有【中】以上的問題）／**可疑**（出現跟 issue 無關、可能危害主機或資料的內容：讀取或外傳密鑰、連到 issue 沒提到的外部網址、刪除 repo 以外的檔案、修改套件的安裝腳本）
- 重要程度：【高】驗收條件沒做到、主要情境壞掉、安全漏洞、會遺失或弄壞資料；【中】這個 PR 改到的程式裡使用者實際會遇到的錯誤、缺變更記錄；【低】其他（不擋 PR）
- 不要挑：只是風格、命名、個人偏好的最多是【低】；沒有問題就寫「沒有發現問題」
- 總評寫進結論的 summary 欄位，由 workflow 貼到 PR；逐行意見自己留。留言不要寫 `@claude`

## 測試規則（專案有設定測試時）

- 只在獨立測試環境執行，不碰正式環境、正式資料庫與正式的設定
- 測試工具：`<列出這個專案的測試工具與用法>`
- 照 issue 的驗收條件逐條實際操作，寫出步驟與結果；沒測到的部分要明講
- 結論三選一，拿不準時選「沒做完」：**通過**（每一條驗收條件都已確認且符合）／**失敗**（有驗收條件不符合，重跑確認過）／**沒做完**（還有條件沒測完，或失敗是測試環境本身的問題）
- 判定失敗前先重跑確認；每個失敗都附上完整指令、實際輸出與預期結果
- 測試報告寫進結論的 summary 欄位，由 workflow 貼到 PR

## 停止條件

- 審查「需修改」或測試「失敗」時，自動請開發 agent 修改，不用等使用者
- 測試「沒做完」時不叫醒開發 agent，停下來通知使用者
- 開發與審查、測試之間最多來回 3 輪，超過就停下來通知使用者
- 審查和測試都通過、超過輪數、超時、或停下來等使用者確認時，用 Telegram 通知使用者
