# 怎麼開 issue

[English](writing-issues.md) | 繁體中文

issue 是交給 AI 的工作單：開發 Claude 照它改程式，審查 Claude 照它檢查有沒有漏做或多做，測試 Claude 照它的驗收條件逐條驗證。寫得越清楚，越少來回修改。

## 兩種 issue

| | 可以開工 | 待規劃 |
|---|---|---|
| 什麼時候用 | 範圍和驗收條件都想清楚了 | 確定要做，但細節還沒想清楚 |
| 範本 | 「AI 新功能」「AI 修錯誤」 | 「待規劃（先記下來）」 |
| 內容 | 背景、要做什麼、不要做什麼、**`## 驗收條件`**、使用者驗證（選填）、補充 | 一兩句：想要什麼結果、為什麼 |
| 標籤 | `feature` 或 `bug`；要開工再加 `ai:*` | 不加類型標籤 |
| 能不能開工 | 可以 | 不行：加了 `ai:*` 也會被擋下 |

待規劃的 issue 之後想清楚了，把內文補成「可以開工」的格式、寫好驗收條件，再加上 `feature`／`bug`。

先跟 AI 助手（或同事）討論清楚範圍與驗收條件再開工，比開工後才改方向便宜得多。

## 開工檢查怎麼認驗收條件

- 要有**單獨一行、一字不差**的 `## 驗收條件` 標題（`###` 也可以，後面多一個冒號沒關係）。寫成 `## 驗收`、`## 驗收標準`、`**驗收條件**`（粗體不是標題）都不算；英文的 `## Acceptance criteria` 也不算
- 標題底下到下一個同層標題之前，至少要有一條實際內容。範本裡的 `<!-- 說明 -->`、空的 `1.`、`-`、`- [ ]` 不算；可以用 `###` 小標題分組
- 檢查的是 issue 當下的內文：補上後不用重開 issue，重新加 `ai:*` 標籤就好

```markdown
## 驗收條件
1. 打開 `/articles?tag=不存在的標籤` 回 404
2. 打開 `/articles` 仍回 200
```

## 每個段落怎麼寫

### 標題
一句話說出結果。
- 好：「文章列表頁碼超出範圍時回 404」
- 不好：「文章列表問題」「修 bug」

### 背景
為什麼要做：現在發生什麼事、誰受影響。bug 要寫怎麼重現：在哪裡、做了什麼、看到什麼、應該看到什麼。

### 要做什麼
要的結果，不用寫怎麼改程式。知道相關的頁面或檔案可以附上。

需求要寫到 AI 不用自己猜：要用的套件、工具或做法寫出確定的一個，不寫「A 或 B」「例如」。真的要交給 AI 判斷的，明寫「由開發 agent 決定」並列出判斷標準。

### 不要做什麼
最常被忽略、但最能避免「多做」的一段。例如：
- 只改文章列表，文章內頁不動
- 不要改資料庫結構
- 不要加新套件

審查 Claude 會對照這段檢查有沒有多做。

### 驗收條件
最重要的一段：審查與測試只看這段下結論，全部符合才算完成。一定要確認的事都要寫在這裡，寫在其他段落的只會順便看。

- **每一條都能回答「是」或「不是」**
- **寫成可以操作確認的句子**：打開哪裡、用什麼身分、應該看到什麼
- **寫出具體的值**：狀態碼、會出現的文字、回傳的欄位
- **只寫審查與測試做得到的**：專案有設定測試時，照專案 `AGENTS.md` 寫的測試能力來寫；只能讀程式確認的標「（讀程式碼確認即可）」。沒設定測試的專案，審查只讀程式碼，驗收條件寫成讀程式碼就能確認的內容
- **別忘了「沒壞掉」**：原本正常的行為要維持，挑一兩個最可能被影響的寫進去
- 「建置成功」「寫變更記錄」這類每次都要做的事，寫在專案的 `AGENTS.md` 就好，不用每張 issue 都寫

| 不好 | 好 |
|---|---|
| 頁面要正常 | `/articles?page=999` 回 404；`/articles?page=2` 仍回 200 |
| 錯誤訊息要清楚 | 密碼少於 8 碼時，畫面出現「密碼至少要 8 個字元」 |
| 管理員才能看 | 未登入打開 `/admin/stats` 會被導到 `/login`；管理員登入後看得到 |
| 畫面好看一點 | 標題改用 `#D4A73B`（讀程式碼確認即可）；好不好看寫在「使用者驗證」 |
| 效能變好 | （很難寫成條件的，先討論要量什麼） |

### 使用者驗證（選填）
要你自己確認、AI 做不到的事：看截圖判斷外觀、在手機實際操作、部署後才看得到的。標題寫成 `## 使用者驗證`，跟驗收條件分開；審查與測試不看這段、不影響結論。

### 補充（選填）
相關的 issue、PR、參考網站，以及你知道但 AI 不一定知道的限制（例如「這個欄位手機 App 也在用，名稱不能改」）。

## 一張 issue 多大

- 一張 issue 只放一個能單獨驗收的改動；大功能拆成幾張，依序開
- 粗略標準：驗收條件 3～6 條寫得完。寫到 10 條以上通常就該拆了
- 有先後關係的，等前一張合併後再開下一張

## 不要在 issue 裡要求的事

- 改規則或自動化設定（`AGENTS.md`、`CLAUDE.md`、`.claude/`、`.github/`）、Dockerfile、compose 檔，或專案另外擋下的套件清單：PR 改到會被固定檢查擋下等你人工審查。這類改動自己改，或在本機跟 AI 助手一起做
- 需要金鑰、帳號，或 repo 以外的東西才做得到的事：開發 Claude 會加上 `blocked` 停下

## 範例

### bug

```markdown
標題：文章列表的標籤不存在時應該回 404

## 背景
打開 `/articles?tag=不存在的標籤` 會顯示空的文章列表、回 200，搜尋引擎會把它當成正常頁面收錄。

## 要做什麼
標籤不存在時回 404，顯示網站的 404 頁。

## 不要做什麼
- 標籤存在、但沒有文章時維持顯示空列表
- 不要動 sitemap

## 驗收條件
1. `/articles?tag=不存在的標籤` 回 404
2. `/articles?tag=<存在的標籤>` 仍回 200，頁面出現該標籤的文章標題
3. `/articles` 仍回 200
```

標籤：`bug`，開工時加 `ai:subscription`。

### feature

```markdown
標題：後台文章列表可以依標題搜尋

## 背景
文章變多以後，後台要一頁頁翻才找得到要改的文章。

## 要做什麼
`/admin/articles` 加一個搜尋框，只列出標題包含關鍵字的文章，網址帶 `?q=關鍵字`。

## 不要做什麼
- 不搜尋內文，只搜標題
- 不要改前台的文章列表

## 驗收條件
1. 管理員打開 `/admin/articles?q=<某篇文章標題裡的一個詞>`，列出那篇文章，沒有列出不含這個詞的文章
2. `/admin/articles?q=完全不會出現的字串` 顯示「找不到文章」
3. 未登入打開 `/admin/articles?q=任何字` 會被導到登入頁

## 使用者驗證
- 搜尋框的位置與樣式
```

標籤：`feature`。

### 待規劃

```markdown
標題：文章內頁加上分享按鈕

讀者想把文章傳給朋友時要自己複製網址，希望有一鍵分享。要支援哪些平台、放哪裡之後再討論。
```

不加標籤。

## 常見的來回原因

| 狀況 | 通常是因為 | 下次怎麼寫 |
|---|---|---|
| 審查一直說「多做」 | 沒寫「不要做什麼」 | 範圍寫清楚 |
| 測試說「沒辦法驗證」 | 驗收條件寫了測試做不到的事 | 移到「使用者驗證」，或寫清楚資料怎麼準備 |
| 通過了，但某件事沒做到 | 那件事只寫在「要做什麼」，沒寫成驗收條件 | 一定要確認的事寫進 `## 驗收條件` |
| 改完跟想的不一樣 | 「要做什麼」寫成怎麼改程式，或只寫了一半 | 寫要的結果，必要時附例子 |
| 被固定檢查擋下 | 改動需要動到規則、`.github/` 或套件清單 | 這類改動自己做 |
