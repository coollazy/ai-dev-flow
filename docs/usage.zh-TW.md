# 日常使用

[English](usage.md) | 繁體中文

## 標籤代表 issue 走到哪一步

| 標籤 | 意思 | 誰加 |
|---|---|---|
| （沒有類型標籤） | 待規劃：確定要做，但還沒想清楚 | — |
| `bug`／`feature` | 規劃好、驗收條件寫好了。**加上本身不會開工** | 你 |
| `ai:subscription`（或你設定的其他 `ai:<服務>`） | 開工，用哪家 AI | 你 |
| `model:<名稱>` | 選用，指定模型 | 你 |
| `blocked` | 開發 Claude 做不出來，等你處理 | 開發 Claude |
| `round-1`～`round-3` | 自動修改到第幾輪 | 流程 |

只有對 repo 有寫入權限的人能加標籤，所以外人沒辦法讓 AI 開工。

## 一張 issue 的一生

1. **寫 issue**：用「AI 新功能」或「AI 修錯誤」範本（會自動帶 `feature`／`bug`），寫法見[怎麼開 issue](writing-issues.zh-TW.md)
2. **開工**：加上 `ai:subscription`。可以在送出 issue 前就在 Labels 勾選，也可以之後再加
   - 開工檢查（不用 AI、不花額度）：要有 `bug`／`feature` 標籤，而且內文有 `## 驗收條件` 段落、底下有內容。缺任何一樣就不開工，拿掉 `ai:*` 標籤，並發 Telegram 通知寫明缺哪一樣；補齊後重新加 `ai:*` 標籤即可
   - 開工時 issue 上會出現一則「開工：用訂閱，模型：…」的留言
3. **開發**：開發 Claude 開分支、改程式、開 PR 到 base 分支，PR 說明會寫 `Closes #<編號>`。做不出來時會在 issue 留言說明卡在哪裡，加上 `blocked`
4. **審查**：PR 一開或有新 commit，審查 Claude 只讀程式碼，結論貼在 PR 的「## 審查總評（版本 xxxxxxx）」
   - **通過** → 有設測試的話接著測試；沒設的話就算通過
   - **需修改** → 自動叫開發 Claude 修改，修完重新審查（第二次起只審這輪的改動，並確認上次的問題修好了沒）
   - **可疑** → 停下來等你看。出現跟 issue 無關、可能危害主機或資料的程式時會這樣判定
5. **測試（選用）**：結論貼在「## 測試報告（版本 xxxxxxx）」：通過／失敗（自動叫開發修改）／沒做完（停下來等你）
6. **通知**：都通過、超過輪數、可疑、被擋下、沒做完時發 Telegram 通知
7. **合併**：你決定（見下面「合併前確認」）

## 通知的意思

| 通知 | 意思 | 你要做什麼 |
|---|---|---|
| ✅ 審查（與測試）通過 | 這個版本可以合併 | 看總評與報告，沒問題就合併 |
| 🛑 超過輪數 | 自動修改了 3 輪還沒過 | 看 PR 留言決定：自己補指示（`@claude`）、拿掉 `round-N` 標籤重新算輪數，或關掉 |
| 🚨 可疑 | 程式裡有跟 issue 無關、可能危險的內容 | 仔細看改動再決定；不要直接合併 |
| ✋ 等你確認 | PR 改到規則、`.github/`、Dockerfile 或你指定的檔案，固定檢查擋下、沒有審查 | 人工審查後自己決定合併 |
| ⚠️ 沒做完 | 測試沒測完，或流程本身出錯、逾時 | 看執行紀錄，必要時重跑 |
| ⛔ issue 還不能開工 | 缺類型標籤或驗收條件 | 補齊後重新加 `ai:*` 標籤 |
| 💬 開發 Claude 回覆了，沒有推新 commit | 被叫醒修改，但只回了留言（例如需要你決定） | 看 PR 留言 |

## 合併前確認

- PR 上**最新**的審查總評（與測試報告）寫的版本，要等於 PR 目前最新的 commit。run 顯示綠燈不代表通過（被取消、被擋下、沒跑的 run 也可能是綠的），一定要看留言
- PR 分支上沒有正在跑或排隊中的 run
- 合併時鎖定審查通過的那個 commit，之後又多了 commit 的話 GitHub 會拒絕：

  ```bash
  gh pr merge <編號> --merge --match-head-commit <通過的 commit>
  ```

- 合併前又推了任何 commit（包括把 base 分支合併進來解衝突），要等新版本重新審查通過

## 中途插手

- **補充或改方向**：在 PR（還沒有 PR 時在 issue）留言 `@claude` 加上指示。只認對 repo 有寫入權限的人的留言
- **收到 `blocked`**：看 issue 上的說明，補上需要的資訊或決定後，拿掉 `blocked`，留言 `@claude 繼續`
- **重新算輪數**：拿掉 PR 上的 `round-N` 標籤
- **不要了**：直接關掉 PR 和 issue。PR 關掉或合併後，流程不會再改它

## 常見問題

| 狀況 | 原因與處理 |
|---|---|
| 加了 `ai:subscription` 沒反應 | 看 Actions 頁的「AI 開發」run。沒有 run：確認呼叫檔已經推到預設分支（issue 事件只看預設分支的 workflow）。有 run 但沒開工：看 run 摘要的「開工檢查」 |
| 開工檢查說缺驗收條件 | 標題要單獨一行、一字不差的 `## 驗收條件`（不能寫成粗體或「驗收標準」），底下至少一條實際內容 |
| PR 沒有審查 | PR 沒有 `ai:*` 標籤，而且它要關閉的 issue 也沒有；從 fork 開的 PR；只改了文件（路徑過濾）；commit 訊息有 `[skip ci]` |
| 開發 Claude 推的 commit 沒觸發審查 | Claude GitHub App 沒有授權這個 repo，推送變成用 `GITHUB_TOKEN`（GitHub 不會讓它觸發其他流程） |
| 「AI 設定有問題」的留言 | `ai:<服務>` 標籤對應的 secret 或變數沒設，見[接其他 AI 服務](providers.zh-TW.md) |
| 審查一直挑出新問題 | 每輪的修改帶進新問題；讓修改範圍跟審查意見對齊，或在 issue 寫清楚「不要做什麼」 |
| 沒有 Telegram 通知 | `TELEGRAM_BOT_TOKEN`／`TELEGRAM_CHAT_ID` 沒設或錯誤；run 裡會有 warning |
